## Context

MVP Phase 3 (41 §42) requires PostgreSQL migrations. Fixed constraints the
toolchain must serve:

```text
- PostgreSQL = the ONLY source of truth; pgvector = initial semantic
  retrieval (40 §5.1; 02 §5 invariants).
- Core purity: core/ must never import infrastructure code. The 4
  import-linter contracts already enforce this; therefore ALL persistence
  code (engine, sessions, table metadata, migrations) lives under
  infrastructure/ only. Core keeps Pydantic contracts + Protocol ports.
- Contract-first (40 §2.1): Pydantic v2 models in core/contracts are the
  single source of entity shape. DB tables map those contracts; they do not
  redefine truth.
- mypy --strict discipline on typed code; ruff; pytest; check_repo.sh is
  the single verification entry point (CI mirrors local).
- Async I/O profile fixed by ADR-0001 (asyncio; FastAPI).
- Migrations must be first-class: schema evolves per phase (identity ->
  execution records -> audit -> memory), with rollback capability (40 §8.2
  change-management and 41 phase order).
- ADR-0001 (ACCEPTED) already sketched "PostgreSQL via SQLAlchemy 2.x
  (typed, async) + Alembic migrations; pgvector via pgvector-sqlalchemy"
  inside the stack listing — but the state file records the persistence
  toolchain as a NEW significant choice requiring its own ADR before any
  dependency lands. This ADR is that decision record.
```

Entities already contracted (Phase 1/2, would be covered by the first
migration): User, Tenant, Workspace, Project (identity.py); audit events
(audit.py) follow in a later migration per phase order.

## Alternatives

### A. SQLAlchemy 2.x (async) + asyncpg driver + Alembic + pgvector-sqlalchemy

Pros:
```text
- SQLAlchemy 2.x has a fully typed, async-native API (AsyncSession,
  Mapped[T] / mapped_column) that passes mypy --strict — matches the
  existing type gate.
- Alembic is the de-facto migration standard, made by the same author;
  autogenerate diffs against table metadata; upgrade/downgrade scripts give
  the rollback capability 40 §8.2 requires.
- pgvector has a maintained SQLAlchemy integration (Vector type) — the
  40 §5.1 semantic-retrieval requirement is a column type, not a fork.
- asyncpg underneath is the fastest Python Postgres driver; SQLAlchemy's
  asyncpg dialect is first-class.
- Table metadata is declarative and lives in infrastructure/db/ — core
  purity holds; repositories implement core ports (same pattern already
  proven with the in-memory bindings).
- Massive ecosystem/documentation; lowest bus-factor risk for a
  single-agent codebase.
```
Cons:
```text
- Two dependency families (sqlalchemy, alembic) + driver; larger surface
  than raw SQL.
- ORM indirection can hide SQL; mitigated by using SQLAlchemy Core
  expressions where clarity matters and reviewing autogenerated migrations
  by hand (autogenerate output is a draft, never committed blind).
```

### B. Raw asyncpg + hand-rolled SQL migration runner

Pros:
```text
- Minimal dependencies (asyncpg only); SQL fully explicit.
- No ORM abstraction cost.
```
Cons:
```text
- A hand-rolled migration runner (version table, ordering, up/down,
  transactional DDL) is real infrastructure we would own, test, and debug —
  reinventing Alembic without its edge-case maturity. High-risk for a
  source-of-truth store.
- asyncpg's own API is loosely typed (Record access is stringly typed);
  every row->contract mapping is hand-written — repetitive and a
  drift-vs-contracts hazard.
- No autogenerate: schema drift between contracts and DDL is caught only by
  human diligence.
```

### C. Lightweight ORM alternatives (SQLModel / Tortoise / Piccolo)

Pros:
```text
- SQLModel unifies Pydantic + table definition in one class.
```
Cons:
```text
- SQLModel would push table definitions INTO the contract layer, violating
  the core-purity boundary (contracts must not know persistence) — a direct
  conflict with the import-linter contract "core.contracts imports no
  implementation".
- Tortoise/Piccolo: smaller ecosystems, weaker mypy --strict stories,
  migration tooling less mature than Alembic; pgvector support marginal.
```

## Decision

**Alternative A**, confined to `infrastructure/`:

```text
Driver:      asyncpg (via SQLAlchemy's postgresql+asyncpg dialect)
ORM layer:   SQLAlchemy 2.x — typed declarative metadata + AsyncSession;
             Core-expression style preferred over heavy ORM features
Migrations:  Alembic (async template), env under infrastructure/db/,
             one reviewed migration per schema change, downgrade required
Vector:      pgvector via the pgvector Python package's SQLAlchemy type
Boundary:    core/ NEVER imports sqlalchemy/alembic/asyncpg — enforced by a
             new import-linter forbidden contract added with the dependency
Mapping:     infrastructure repositories implement core ports and convert
             rows <-> core/contracts Pydantic models at the boundary
Testing:     migration smoke tests (upgrade head + downgrade base) once a
             real/ephemeral Postgres is available; until then metadata
             import + offline SQL compile checks keep gates hermetic
```

## Reason

```text
- Alembic is the only alternative with mature up/down migrations — 40 §8.2
  rollback and the multi-phase schema evolution demand it; hand-rolling a
  runner (B) concentrates risk exactly on the source of truth.
- SQLAlchemy 2.x typed API preserves the mypy --strict gate; raw asyncpg
  (B) weakens typing precisely at the persistence boundary.
- Option C's SQLModel breaks the contracts-are-pure invariant outright;
  the smaller ORMs trade away migration maturity for nothing we need.
- Consistent with ADR-0001's ACCEPTED stack sketch — this ADR is a
  confirmation-with-analysis, not a reversal, minimizing decision churn.
```

## Consequences

```text
+ First migration can cover the contracted identity/tenancy entities
  immediately after acceptance; audit/execution tables follow phase order.
+ Autogenerate (used as reviewed draft) catches contract/schema drift.
- New runtime deps: sqlalchemy>=2, alembic, asyncpg, pgvector — pinned in
  pyproject.toml only AFTER this ADR is ACCEPTED.
- A 5th import-linter contract must land with the dependency (core must not
  import sqlalchemy/alembic/asyncpg).
- Real-DB integration tests need an ephemeral Postgres (compose or
  testcontainers) — that test-infra choice rides with the implementation
  task, not a separate ADR, unless it adds heavyweight tooling.
Rollback: repositories implement core ports; swapping the toolchain later
replaces infrastructure/db/ only — contracts and core services untouched.
```
